# Заметки по RouterOS, проверенные на железе

Всё ниже проверено на hAP ax^2 (arm64) с RouterOS 7.24.1. Проверить заново на
новой версии можно скриптом `probe.rsc`.

## Область видимости и `:parse`

Модуль, загруженный через `[:parse $content]`, получает **свою** область
видимости и не видит `:local` вызывающего. Единственный канал между
`install.rsc` и модулями — глобальные переменные, отсюда префикс `m` у всех
имён библиотеки и единственная точка очистки
`/system/script/environment/remove [find]` в самом конце `install.rsc`.
Модуль не имеет права чистить окружение — он снесёт функции, которыми
пользуется всё остальное.

## Хеширование

`:convert` умеет `transform=md5` и `transform=sha512`. Форма вызова:

```routeros
:convert $text transform=md5 to=hex
```

Без `to=hex` возвращаются сырые байты. Проверено на строке в 4000 символов.
Результат совпадает с `hashlib.md5` в Python байт в байт, поэтому манифест
можно генерировать на компьютере, а сверять на роутере.

Из этого следует требование к переводам строк: файлы обязаны храниться с LF.
CRLF-выгрузка даст другой хеш, и обнаружение обновлений сломается. За этим
следит `.gitattributes` и проверка в `tools/gen_manifest.py`.

## `:len` считает байты

Три кириллические буквы дают `:len` = 6. Поэтому любое выравнивание колонок
паддингом на кириллице разъезжается, и весь вывод держим в ASCII.

Любопытно, что сама кириллица через SSH проходит и отображается корректно —
распространённое утверждение «в консоли ломается» на 7.24.1 не подтвердилось.
Но проблема с `:len` остаётся, и поведение зависит от клиента.

## Пустой массив

`{}` — синтаксическая ошибка. Пустой массив создаётся как `[:toarray ""]`.

## Комментарии

`#` работает только в начале строки. Комментарий после кода на той же строке
даёт `expected end of command`.

## Переменная не должна называться как свойство

Это самая коварная находка. Внутри `[find where name=$name]` RouterOS
разрешает `$name` в **свойство** элемента, а не в вашу локальную переменную,
и поиск возвращает не то. Называйте переменную иначе — в `50-lists.rsc` она
называется `sname` именно поэтому.

## У контейнера нет свойства `status`

На 7.24.1 состояние читается только флагами `running` и `stopped`, причём
`running` возвращает пустую строку, а не `false`. Обёртка — `$mContState` в
`lib.rsc`.

## `/file add contents=` работает

На 7.24.1 создать файл с содержимым можно напрямую, хотя старые обсуждения на
форуме утверждают обратное. Состояние установщика мы всё равно храним в
`/system script`, потому что скрипт можно сразу `[:parse]`.

## Выполнение команд по SSH

Через `ssh admin@host "команда"` путь **без ведущего слэша**:
`system resource print` работает, `/system resource print` даёт
`expected command name`. Скриптовая форма `:put [/system resource get version]`
работает как есть.

## `/tool fetch` и схема

`mode=` должен совпадать со схемой URL. Локальный HTTP-сервер разработки с
`mode=https` не откроется — в `$mFetch` схема выбирается по префиксу URL.

## Проверка DoH: `servers=` обязана быть пустой

При сбое DoH RouterOS молча откатывается на обычный список `/ip dns servers`.
Поэтому измерять доступность DoH, оставив там хоть что-нибудь, бессмысленно:
любой результат превращается в ложный «работает». Правильный тест — пустой
`servers`, статические A-записи для хостнеймов эндпоинтов (иначе их нечем
резолвить) и контрольный прогон без резолверов вообще, который обязан упасть.

Замер на hAP ax^2 / 7.24.1 в сентябре 2026, три прогона на каждую строку:

| эндпоинт | verify=no | verify=yes |
|---|---|---|
| `https://8.8.8.8/dns-query` | работает | работает |
| `https://dns.google/dns-query` | работает | работает |
| `https://1.1.1.1/dns-query` | работает | **падает 3/3** |
| `https://one.one.one.one/dns-query` | работает | падает |
| `https://cloudflare-dns.com/dns-query` | работает | падает |
| `https://9.9.9.9/dns-query` | работает | работает |
| `https://dns.quad9.net/dns-query` | нестабильно | работает |

В первой версии этой таблицы была ещё строка про DoH Яндекса с пометкой, что
проверка сертификата у него падает. Это была ошибка замера, а не свойство
Яндекса: я запинил для `common.dot.dns.yandex.net` адрес `77.88.8.78`, тогда как
имя резолвится в `77.88.8.8`. При неверном адресе `verify=no` проходит, а
`verify=yes` закономерно падает — и получается вывод про сервер, который на
самом деле про тест. С правильным адресом DoH Яндекса отвечает три раза из трёх
и с проверкой, и без.

Мораль общая: пиннинг A-записей в тестах DoH нужен, но неверный пин выглядит
ровно как отказ сервера в проверке сертификата. Адрес надо брать из реального
`:resolve`, а не по памяти.

Оговорка: на тестовом роутере вручную импортирован корневой GlobalSign под
именем `Yandex_DoH`, и именно он позволяет цепочке Яндекса провериться. На
чистом роутере без него результат может быть другим — после импорта бандла
Mozilla работает в любом случае.

`builtin-trust-store` при этом был выставлен в `container,dns`, то есть дело не
в отсутствии корневых сертификатов. Вывод для кода: forwarder-ы Cloudflare
заводятся с `verify-doh-cert=no`, иначе они просто не работают.

## `:typeof` от неудачного `:find` — это `nil`

Проверка «есть ли подстрока» пишется так:

```routeros
:if ([:typeof [:find $haystack "needle"]] != "num") do={ ... не найдено ... }
```

Ошибка `= "nothing"` не сработает: `nothing` — это про переменную, которой
никогда не присваивали значение, а неудачный `:find` возвращает `nil`. Сравнение
с `"nothing"` молча означает «подстрока найдена» и пропускает нужную ветку.

## `builtin-trust-store` действует пословно, по сервисам

Значение вида `container,dns` означает, что встроенный набор корневых
сертификатов виден **только** контейнерам и DNS. У `/tool fetch` в этом случае
нет ни одного корня, и `check-certificate=yes` всегда падает с
`ssl: no trusted CA certificate found`. Замер:

```
trust store: container,dns
  check-certificate=no  -> ok
  check-certificate=yes -> failure: ssl: no trusted CA certificate found
trust store: fetch,container,dns
  check-certificate=no  -> ok
  check-certificate=yes -> ok
```

Для проекта это существенно: установщик скачивает скрипты и выполняет их через
`[:parse]`, то есть непроверенный TLS здесь — канал выполнения кода. Поэтому
`install.rsc` добавляет `fetch` в trust store ещё в preflight, а `$mFetch`
сначала пробует `check-certificate=yes` и лишь потом откатывается на `no`,
один раз громко предупредив.

Смена `builtin-trust-store` вступает в силу не мгновенно: сразу после записи
проверенный fetch ещё падает, а через пару секунд начинает работать. Замер:

```
immediately after adding fetch:  FAILED
after 2s more:                   finished
```

Поэтому после изменения настройки стоит `:delay 3`.

Там же нашлась причина, по которой Cloudflare DoH не проходит проверку:
RouterOS отвечает `ssl: no trusted CA certificate found` и для `1.1.1.1`, и для
`one.one.one.one`, и для `cloudflare-dns.com`, тогда как Google и Quad9 при том
же trust store проверяются нормально. То есть дело не в несовпадении имени и не
в сервере, а в том, что удостоверяющего центра Cloudflare просто нет в наборе,
который поставляется с RouterOS.

## Булево свойство читается пустым, когда оно true

`/ip/dns/forwarders/get <id> verify-doh-cert` возвращает пустую строку, если
проверка включена, и `false`, если выключена. Поэтому фильтр
`find where verify-doh-cert=yes` не находит ничего, и написанный на нём откат
настройки молча не срабатывает. Фильтровать по `=no` можно, по `=yes` нельзя.
Надёжнее выбрать элементы по имени и выставить значение всем.

## Импорт корневых сертификатов

RouterOS не может проверить сертификат Cloudflare — ни по `1.1.1.1`, ни по
`one.one.one.one`, ни по `cloudflare-dns.com` — потому что подписавшего его
удостоверяющего центра нет во встроенном наборе. Импорт бандла Mozilla с
`https://curl.se/ca/cacert.pem` это чинит: после него DoH Cloudflare проходит
с `verify-doh-cert=yes` три раза из трёх, и проверенный `/tool fetch` тоже.

Бандл на сентябрь 2026 — около 189 КБ и 120 сертификатов, все приходят уже
доверенными. Импортированные корни работают независимо от того, что перечислено
в `builtin-trust-store`: проверенный fetch заработал даже при
`builtin-trust-store=container,dns`.

Импорт стоит делать отложенным разбором:

```routeros
/tool fetch url="https://curl.se/ca/cacert.pem" mode=https check-certificate=no dst-path="cacert.pem"
:delay 2
:local imp [:parse "/certificate/import file-name=cacert.pem passphrase=\"\""]
$imp
```

`file-name=` разбирается в момент парсинга блока, а не выполнения строки, так
что импорт, написанный рядом со скачиванием, может упасть ещё до запуска. На
7.24.1 прямая форма отработала, но отложенная не зависит от этого везения.

## Какому резолверу какой корень нужен

Цепочки, снятые с самих серверов:

| эндпоинт | промежуточный | корень | есть у RouterOS |
|---|---|---|---|
| `1.1.1.1`, `cloudflare-dns.com` | SSL.com SSL Intermediate CA ECC R2 | **SSL.com Root Certification Authority ECC** | **нет** |
| `dns.google` | WE2 (Google Trust Services) | GTS Root R4 → GlobalSign Root CA | да |
| `common.dot.dns.yandex.net` | GlobalSign RSA OV SSL CA 2018 | GlobalSign Root CA - R3 | да |

То есть весь «Cloudflare не проходит проверку» сводится ровно к одному
отсутствующему корню SSL.com. Импорт только его чинит и `1.1.1.1`, и
`one.one.one.one` — три прогона из трёх с `verify-doh-cert=yes`. Тянуть ради
этого весь бандл на 120 сертификатов не обязательно.

Яндекс, вопреки распространённому мнению, проверяется штатным набором RouterOS.
Проверено отдельно: если пометить вручную импортированный на роутере корень
GlobalSign как недоверенный, DoH Яндекса всё равно проходит с проверкой три
раза из трёх. Значит дело не в нём.

## CRL для этого не нужен

`/certificate settings` по умолчанию идёт с `crl-download=no` и `crl-use=no`, и
проверка сертификатов при этом работает — все замеры выше сделаны именно в этой
конфигурации. Включать CRL означает поставить каждую проверку в зависимость от
доступности точки распространения списка отзыва, то есть добавить ещё один
способ сломать DNS на роутере, у которого вы этот самый DNS и чините.

## НСДИ резолвит только домашние имена, и не может стоять первым

Замер на роутере:

| upstream | `raw.githubusercontent.com` | `github.com` | `ghcr.io` | `curl.se` |
|---|---|---|---|---|
| `194.85.254.37` НСДИ | SERVFAIL | SERVFAIL | SERVFAIL | SERVFAIL |
| `77.88.8.8` Яндекс | 185.199.109.133 | 140.82.121.3 | 140.82.121.33 | 151.101.65.91 |

И, что важнее, RouterOS считает SERVFAIL от первого сервера окончательным
ответом, а не поводом спросить следующий:

```
servers=194.85.254.37,77.88.8.8          raw.githubusercontent.com -> FAIL
servers=77.88.8.8,77.88.8.1,194.85.254.37 raw.githubusercontent.com -> 185.199.108.133
```

Поэтому в `$mFallbackServers` НСДИ идёт вторым. Если поставить его первым,
перестают работать сразу три вещи: скачивание модулей самим установщиком,
скачивание образов контейнеров с `ghcr.io` и загрузка бандла сертификатов с
`curl.se`. Найдено при первом же запуске опубликованного установщика.
