# scripts-ros

Модульный установщик для RouterOS. Вместо одного монолита на 30 КБ — маленький
загрузчик, общая библиотека и набор модулей, которые качаются по одному и
выполняются из оперативки.

Меню показывает, что уже настроено на этом роутере, и позволяет доустановить
только недостающее. Всё идемпотентно: повторный запуск ничего не ломает и
честно пишет `[ == ]` там, где менять нечего.

```
==============================================
 10 [ ok ] Base settings       dns 8 fwd, ntp synced, ipv6 off
 20 [ ok ] Container storage   tmp1 tmpfs, 476 MiB free, repull ok
 30 [ ~~ ] MihomoProxyRoS      STOPPED, 138 envs
 40 [ -- ] DNSProxy            not installed
 41 [ -- ] AdGuard Home        not installed
 50 [upd ] Resource lists      4 of 4 installed, 1 UPDATE
 60 [ ok ] Proxy link / sub    LINK1 vless://ba..., SUB set

  a   [    ] install everything
  s   [    ] full status report
  x   [    ] remove everything
  q   [    ] quit
==============================================
```

Номер строки — это номер модуля, поэтому по строке сразу видно, какой файл она
запускает. После выбора строки установщик спрашивает, что с ней сделать:

```
  MihomoProxyRoS: [ ~~ ] STOPPED, 138 envs
   1) install or repair
   2) remove
   3) back
```

Удаление всегда касается **только выбранной строки**. Снести один контейнер,
не тронув остальную настройку, — обычная операция, а не повод искать отдельный
uninstall.


## Требования

* **RouterOS 7.24.1 или новее.** Ниже установщик откажется работать.
  7.24.0 отсекается отдельно: в ней сломан поиск аргументов в консольной
  команде `find`, а весь проект построен на `find where comment=`.
* Включённый режим контейнеров — нужен только для пунктов 2, 3 и 4:

```
/system/device-mode/print
/system/device-mode/update mode=advanced container=yes traffic-gen=yes
```

На подтверждение даётся около 5 минут: выключите и включите питание либо
кратковременно нажмите любую физическую кнопку на устройстве.

## Запуск

Вставьте в терминал RouterOS целиком. Первый блок — обход блокировки диапазонов
Fastly, на которых живёт `raw.githubusercontent.com`. Он обязан быть **здесь**,
а не внутри скачиваемого файла: без него скачивать нечем.

```routeros
/ip firewall nat
:if ([:len [find where comment="GitHub_Fastly_fix_dstnat"]] = 0) do={add action=netmap chain=dstnat dst-address=185.199.108.0/22 to-addresses=185.199.109.0/24 comment="GitHub_Fastly_fix_dstnat"}
:if ([:len [find where comment="GitHub_Fastly_fix_output"]] = 0) do={add action=netmap chain=output dst-address=185.199.108.0/22 to-addresses=185.199.109.0/24 comment="GitHub_Fastly_fix_output"}
:if ([:len [find where comment="GitHub_Fastly_133_to_154_dstnat"]] = 0) do={:foreach a in={"185.199.108.133";"185.199.109.133";"185.199.110.133";"185.199.111.133"} do={add action=dst-nat chain=dstnat dst-address=$a dst-port=443 protocol=tcp to-addresses=([:pick $a 0 ([:len $a] - 3)] . "154") comment="GitHub_Fastly_133_to_154_dstnat" place-before=[find where comment="GitHub_Fastly_fix_dstnat"]}}
:if ([:len [find where comment="GitHub_Fastly_133_to_154_output"]] = 0) do={:foreach a in={"185.199.108.133";"185.199.109.133";"185.199.110.133";"185.199.111.133"} do={add action=dst-nat chain=output dst-address=$a dst-port=443 protocol=tcp to-addresses=([:pick $a 0 ([:len $a] - 3)] . "154") comment="GitHub_Fastly_133_to_154_output" place-before=[find where comment="GitHub_Fastly_fix_output"]}}

/system/script/environment/remove [find]
:global r [/tool fetch url="https://raw.githubusercontent.com/Medium1992/scripts-ros/refs/heads/main/install.rsc" mode=https output=user as-value]
:global s [:parse ($r->"data")]
$s
```

`/system/script/environment/remove [find]` стоит там не для красоты: глобальные
переменные переживают запуск, и забытая с прошлого раза `mBase` увела бы
установку на чужой источник.

Загрузчик сам проверит версию, подтянет библиотеку и покажет меню. Выбор —
цифрой.

Если `fetch` всё равно не проходит, значит роутеру нечем резолвить имена. Дайте
ему рабочий резолвер и повторите:

```routeros
/ip dns set servers=77.88.8.8,77.88.8.1 use-doh-server=""
/ip dns cache flush
```

## Из чего состоит

| файл | назначение |
|---|---|
| `install.rsc` | единственное, что вставляется руками: preflight, меню, запуск модулей |
| `lib.rsc` | общие функции: вывод, идемпотентность, ввод, fetch, md5, состояние |
| `status.rsc` | живые проверки состояния для строк меню |
| `manifest.rsc` | md5 всех обновляемых файлов, генерируется `tools/gen_manifest.py` |
| `modules/` | сами модули |
| `lists/` | движок обновления списков и наборы ресурсов |
| `assets/` | скрипты, которые ставятся на роутер как есть |

## Что удаление НЕ трогает

* **Ваши статические записи DNS и address-list.** Фрагменты, которые тянет
  загрузчик, комментируют каждую запись именем своего фрагмента
  (`category-gov-ru`, `telegram`, `deepl`), а добавленное руками комментария не
  имеет либо имеет своё. Удаление читает имена фрагментов из **ваших**
  companion-списков и убирает только записи с ровно такими комментариями.
  Остальное не считается и не трогается — в выводе прямо пишется, сколько
  чужих FWD-записей остаётся на месте.

* **Базовые настройки как состояние роутера.** `10-base-remove` снимает
  объекты — forwarders, blackhole-маршруты, обход GitHub Fastly. Но IPv6
  остаётся выключенным, NTP включённым, hardening применённым: это не объекты,
  а состояние, и прежнего значения, к которому можно вернуться, попросту нет.
  Включать обратно IPv6 на работающем роутере — самодеятельность.
* **Ваши списки ресурсов** (`FWD_update_list` и такие же) — спрашивается
  отдельно, по умолчанию остаются.
* **Наполненные данные** — десятки тысяч записей в address-list и FWD.
  Удаляются минутами и без mangle-правил безвредны, поэтому тоже отдельный
  вопрос.
* **Конфиг AdGuard Home** в `/adguard_conf/` — по умолчанию переживает
  удаление контейнера, повторная установка его подхватит.

## Два режима MihomoProxyRoS

Строка 30 спрашивает, что именно ставить:

```
   1) full      container + redirection policy for the whole LAN
   2) container working proxy with its routes, nothing redirected yet
   3) back
```

Граница проходит по тому, **что решает, какой трафик туда попадёт**, а не по
тому, что делает контейнер работоспособным.

| | container | full |
|---|---|---|
| veth, адрес `192.168.255.1/30`, InAccept, Containers, forwarder | да | да |
| таблица `MihomoProxyRoS` и маршрут `0.0.0.0/0` в контейнер | да | да |
| blackhole приватных сетей в этой таблице | да | да |
| маршрут `198.18.0.0/15` — контейнер работает с fake-ip по умолчанию | да | да |
| mount-ы, pull образа, запуск, ссылка и подписка | да | да |
| mangle: маркировка соединений и маршрутов | **нет** | да |
| env с группами, geosite, AS и правилами | **нет** | да |
| статический DNS и firewall address-list | **нет** | да |

После `container` вы получаете поднятый и достижимый прокси с готовым
маршрутом — остаётся решить, что в него направить: записью
`forward-to=MihomoProxyRoS` в статическом DNS или собственной маркировкой в
таблицу `MihomoProxyRoS`. Групповая политика при этом не применяется, mihomo
работает на своих умолчаниях.

Ставить контейнер без таблицы и маршрута смысла нет: это не более лёгкая
установка, а неработающая. Поэтому вся обвязка ставится всегда.

Режим хранится в состоянии и виден в строке меню (`full, running, 138 envs`).
Дойти из `container` до `full` — это просто ещё раз строка 30, остальное
переставляться не будет.

## Кто отвечает за DNS роутера

По умолчанию — никто. `10-base` спрашивает, чем роутер резолвит имена, пока
никто другой не взялся:

```
  base resolver, used until something else takes over (arm64)
   1) Yandex DoH, plain Yandex behind it   <- suggested here
   2) Yandex plain DNS only
   3) Quad9 DoH, plain Quad9 behind it
   4) NSDI first, Yandex behind it (domestic names resolve first)
```

Подсказка зависит от архитектуры: на **arm64 и x86/CHR** предлагается DoH
Яндекса, на остальных — обычный Яндекс по 53, потому что HTTP/2 для DoH есть
только на первой паре и DoH там может просто не ответить. Обычные серверы
держатся и позади DoH: при сбое DoH-запроса RouterOS уходит на них, что для
резервного пути именно то, что нужно.

**Почему не НСДИ первым.** НСДИ отвечает SERVFAIL на любые зарубежные имена —
`github.com`, `ghcr.io`, `curl.se`, — а RouterOS считает отказ первого сервера
окончательным и следующий не спрашивает. С НСДИ во главе списка ломается сразу
всё: загрузка модулей установщиком, скачивание образов и загрузка бандла
сертификатов. Поэтому вариант 4 существует, но по умолчанию впереди Яндекс.

Выбор хранится в состоянии (`fb_doh`, `fb_servers`), его читают и сторож
`changeDNS`, и удаление контейнеров-резолверов.

DoH-forwarder-ы при этом заводятся и остаются полезными: через них ходит уже
проксированный трафик, и на них можно направлять списки доменов. Заводятся
парами — по IP и по имени: `Google` / `Google-Host`, `CloudFlare` /
`CloudFlare-Host` (`one.one.one.one`), `Quad9` / `Quad9-Host`.

Каждый провайдер заводится тремя форвардерами, чтобы вариант читался прямо из
имени:

| имя | что это |
|---|---|
| `CloudFlare` | DoH с проверкой сертификата — вариант по умолчанию |
| `CloudFlare_noverify` | тот же DoH, проверка выключена |
| `CloudFlare_udp` | обычный DNS по 53 |

Так для `Google`, `GoogleHost`, `CloudFlare`, `CloudFlareHost`, `Quad9`,
`Quad9Host`, `Yandex`, `XBOX`, плюс `NSDI_udp` и `Fallback_udp`. Все они
попадают в меню выбора при установке списков доменов.

`_noverify` существует потому, что RouterOS не может проверить сертификат
Cloudflare: его цепочка идёт к корню **SSL.com Root Certification Authority
ECC**, которого нет во встроенном наборе. Модуль `16-cacert` это чинит и
предлагает два пути:

* **targeted** — импортировать только нужные корни. Они лежат в репозитории с
  sha256 в заголовке файла, так что видно, что именно ставится, и оно не
  меняется само. Один сертификат — и Cloudflare проходит с проверкой три раза
  из трёх.
* **bundle** — весь набор Mozilla с curl.se: чинит что угодно, но добавляет
  около 120 записей, и саму эту загрузку проверить нечем.

После импорта `16-cacert` сам поднимает форвардерам Cloudflare
`verify-doh-cert=yes`, и `_noverify` остаётся только диагностическим.

CRL включать не нужно: `crl-download` и `crl-use` по умолчанию выключены, и
проверка работает без них.

### Платформа

DoH поверх HTTP/2 появился в RouterOS 7.23 **только для ARM64 и x86/CHR**. На
остальных архитектурах DoH остаётся на HTTP/1.1, и резолвер, которому нужен
HTTP/2, там просто не ответит — выглядит это как сломанный форвардер, а не как
неподдерживаемая платформа. Поэтому `11-dns` на таких железках предупреждает, а
строка 17 даёт померить на месте, вместо того чтобы гадать про каждого
провайдера. arm32 в проекте целевой платформой не считается.

Строка 17 полезна и на arm64: форвардер, который существует, и форвардер,
который отвечает, — разные вещи. Пример вывода, где сразу видно отсутствующий
корень Cloudflare:

```
  forwarder               result  certificate
  Google                  ok      verify=true
  CloudFlare              FAILS   verify=true
  CloudFlare_noverify     ok      verify=false
  Quad9                   ok      verify=true
  Yandex                  ok      verify=true
  [ ++ ] 14 of 17 DoH forwarder(s) answered
```

Чем платите при `verify=no`: канал остаётся зашифрованным, но перестаёт быть
аутентифицированным. Любой, кто может перехватить маршрут до `1.1.1.1`,
терминирует TLS и отдаст свои DNS-ответы — то есть ровно тот противник, ради
которого DoH и нужен. Замеры и цепочки сертификатов в
[docs/routeros-notes.md](docs/routeros-notes.md).

Строки 40 и 41 могут забрать роль резолвера себе, но это **всегда вопрос**, и
ответ «нет» — полноценный вариант:

```
  DNSProxy can become the routers resolver, with automatic
  fallback to 194.85.254.37,77.88.8.8 whenever it is not running.
  Answering no leaves /ip dns untouched -- the container still works,
  you just send it the domains you choose instead of everything.
  Make DNSProxy the router resolver? [y/n]
```

Отказаться можно обоим. Контейнер при этом работает, просто домены на него
направляются точечно через `forward-to=`, а не весь трафик разом.

Возможные состояния:

| ситуация | что спросит |
|---|---|
| роль ничья | «сделать этот контейнер резолвером?» |
| роль у другого контейнера | «передать её этому вместо того?» |
| роль уже у этого контейнера | «вернуть резолвер на фолбэк?» |

Владелец записан в состояние (`resolver`, `resolver_addr`), сторож `changeDNS`
каждые 10 секунд следит за его контейнером: работает — `/ip dns` смотрит на
него, упал или удалён — уходит на фолбэк.

**Сторож ровно один, независимо от числа контейнеров.** Два независимых сторожа
видели бы чужое значение как неправильное и переписывали бы его каждые 10
секунд, вечно. Поэтому цель хранится в состоянии, а вся логика — в
`45-resolver`, который вызывается и строкой 40, и строкой 41.

Если роль не отдавали никому, удаление контейнера `/ip dns` не трогает вообще.

В строке меню владелец помечен словом `RESOLVER`, в полном отчёте есть поля
`resolver owner` и `watchdog DNSchange`.

## Списки ресурсов: движок отдельно, данные отдельно

При первой установке каждого списка установщик спрашивает, **в какой forwarder**
слать домены, и показывает те, что реально есть на этом роутере:

```
  where should FWD_update_list forward its domains?
   1) Google
   2) Yandex
   3) MihomoProxyRoS   <- suggested
   4) AdGuardHome
  number, or Enter for MihomoProxyRoS:
```

Поэтому порядок имеет смысл: поставьте сначала строку 40 или 41, и их
forwarder появится в этом списке — списки доменов можно направить в AdGuard
или DNSProxy, а не только в прокси. Выбор дописывается отдельной строкой в
конец вашего списка и правится потом руками.

Скрипты `FWD_update`, `FWD_update_RU` и `IP_MihomoProxyRoS` — это один и тот же
движок (`lists/engine.rsc`) плюс ваш персональный список ресурсов
(`FWD_update_list` и такие же). Движок обновляется из репозитория, **ваш список
после первой установки не трогается никогда**. Поэтому добавление или удаление
сайтов в вашем списке не конфликтует с обновлением движка.

Если вы всё-таки правите сам движок, работает трёхстороннее сравнение по md5:

| ваша копия | апстрим | что произойдёт |
|---|---|---|
| не менялась | изменился | тихо обновится |
| вы правили | не менялся | останется как есть |
| вы правили | изменился | спросит: оставить / взять новое / пропустить |

Предыдущая версия всегда сохраняется рядом как `<имя>_bak`.

## Локальная разработка

Установщик умеет брать файлы не с GitHub, а с любого HTTP-сервера. Переменная
называется `mDev`, и она специально отдельная от `mBase`: глобальные переменные
переживают запуск в `/system/script/environment`, и забытая `mBase` тихо увела
бы установку на чужой сервер.

```routeros
:global mDev "http://192.168.88.10:8000"
```

Сбросить обратно на GitHub: `:global mDev ""` или
`/system/script/environment/remove [find]`.

```bash
python -m http.server 8000        # в корне репозитория
```

Ещё есть ветка: `:global mBranch "dev"` до запуска загрузчика.

Для работы с тестовым роутером положите рядом файл `.lab` (он в `.gitignore`):

```
HOST=192.168.88.3
USER=admin
PASS=...
```

```bash
python tools/ros.py cmd   "system resource print"
python tools/ros.py run   probe.rsc
python tools/ros.py check lib.rsc modules/*.rsc   # синтаксис глазами RouterOS
```

`tools/ros.py check` заливает файлы на роутер и просит его собственный парсер
их разобрать, ничего не выполняя. Локальный линтер не знает правил RouterOS,
а роутер знает.

`probe.rsc` проверяет примитивы, на которые опирается библиотека: md5 через
`:convert`, `:retry`, `/file add contents=`, побайтовый `:len`. Запускайте его
после выхода новой версии RouterOS.

## Почему весь вывод на английском

RouterOS не работает с многобайтовыми кодировками в консоли, а `:len` считает
байты, а не символы — из-за этого таблица статусов с кириллицей разъезжается.
Поэтому весь рантайм ASCII, а русский живёт здесь, в документации.

## Ограничения

* Модули с `/terminal ask` (2, 4, 5, 6 и `14-hardening`) интерактивные —
  из планировщика их запускать нельзя.
* Строки 40 и 41 обе умеют быть резолвером роутера, но владелец всегда один:
  установщик спросит, отбирать ли роль у текущего владельца.
